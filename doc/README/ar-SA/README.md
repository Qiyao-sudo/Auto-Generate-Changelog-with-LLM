# 🚀 توليد سجل التغييرات تلقائيًا باستخدام نموذج لغة كبير (LLM)

🌐 **اللغات**: [English](doc/README/en-US/README.md) | [中文](doc/README/zh-CN/README.md) | [日本語](doc/README/ja-JP/README.md) | [Deutsch](doc/README/de-DE/README.md) | [Español](doc/README/es-ES/README.md) | [Русский](doc/README/ru-RU/README.md) | [العربية](doc/README/ar-SA/README.md) | [繁體中文](doc/README/zh-TW/README.md)

أداة تلقائية تعتمد على GitHub Actions تستخدم نماذج اللغة الكبيرة (LLM) مثل DeepSeek لتوليد سجلات التغييرات (Changelog) المنظمة والمتстандарتة تلقائيًا. لا داعي للكتابة يدويًا، فقط قم بتشغيل سير العمل للحصول على وثائق تحديثات ذات مستوى احترافي.

## ✨ الميزات

- 🤖 **تحليل ذكي**: يعتمد على LLM لتحليل سجلات Git بذكاء، ويقوم التصنيف التلقائي إلى ميزات جديدة، تحسينات الأداء، إصلاحات أخطاء، إلخ.
- 🏷️ **إدارة العلامات التلقائية**: تدعم إنشاء علامات Git تلقائيًا وحساب اختلافات الإصدارات بذكاء.
- 📁 **تخزين منظم**: تخزن وثائق سجل التغييرات المولدة بشكل هرمي حسب الإصدار الرئيسي والفرعي.
- 🎨 **قوالب احترافية**: تقدم قوالب Markdown معيارية بنمط خروج موحد وجذاب.
- 🔧 **قابل للتكوين عاليًا**: تدعم API LLM المخصصة، والنماذج، وقوالب التعليمات، وغيرها من المعلمات.
- ⚡ **تشغيل بضغطة زر واحدة**: يتم تشغيله يدويًا عبر GitHub Actions، ما عليك سوى إدخال رقم الإصدار لتوليده تلقائيًا.

## 🚀 بداية سريعة

### المتطلبات الأساسية

1. **مستودع GitHub**: تم تمكين GitHub Actions
2. **مفتاح API LLM**: مفتاح API لـ DeepSeek أو خدمات LLM الأخرى المتوافقة مع API OpenAI
3. **بيئة Python**: بيئة Ubuntu في GitHub Actions (مضبوطة تلقائيًا)

### خطوات التثبيت

1. **نسخ ملف سير العمل**: أضف `.github/workflows/generate-changelog.yml` إلى نفس المسار في مستودعك
2. **نسخ ملفات السكربت**: أضف دليل `.github/workflows/scripts/` إلى مستودعك
3. **تكوين أسرار (Secrets)**: أضف الأسرار التالية في إعدادات المستودع → Secrets and variables → Actions:
   - `LLM_API_KEY`: مفتاح API LLM الخاص بك
   - (اختياري) `LLM_API_ENDPOINT`: نقطة نهاية API LLM، بشكل افتراضي DeepSeek
   - (اختياري) `LLM_API_MODEL`: اسم النموذج المستخدم، بشكل افتراضي `deepseek-v4-flash`

## 📖 طريقة الاستخدام

### تشغيل سير العمل يدويًا

1. انتقل إلى صفحة **Actions** في مستودعك على GitHub
2. حدد سير العمل **Auto Generate Changelog with DeepSeek**
3. اضغط على زر **Run workflow**
4. أدخل المعلمات التالية:
   - **main_version**: رقم الإصدار الرئيسي (على سبيل المثال، `1.X`)
   - **sub_version**: رقم الإصدار الكامل (على سبيل المثال، `1.X.X`)
   - **current_tag**: اسم علامة Git الحالية (على سبيل المثال، `v1.X.X`، سيتم إنشاؤها تلقائيًا إذا لم تكن موجودة)

### عملية تنفيذ سير العمل

1. **استخراج الكود**: استخراج تاريخ Git الكامل وجميع العلامات
2. **معالجة العلامات**: التحقق من وجود العلامة المحددة، إنشاؤها إذا لم تكن موجودة
3. **تحليل اختلافات المراجع**: حساب اختلافات المراجع مع الإصدار السابق بذكاء
4. **توليد LLM**: استدعاء API DeepSeek لتوليد سجل تغييرات منظم
5. **حفظ الملف**: حفظ المستند المولود في `doc/Changelogs/{الإصدار الرئيسي}/{الإصدار الفرعي}/App.md`
6. **المراجعة التلقائية**: إضافة ملف سجل التغييرات المولود إلى المستودع
7. **دفع العلامة**: إذا كانت علامة جديدة، يتم دفعها تلقائيًا إلى المستودع البعيد

## ⚙️ تعليمات التكوين

### تكوين متغيرات البيئة

قم بتكوين المتغيرات التالية في GitHub Secrets:

| اسم المتغير | مطلوب | القيمة الافتراضية | الوصف |
|------------|--------|------------------|--------|
| `LLM_API_KEY` | ✅ | لا شيء | مفتاح API LLM |
| `LLM_API_ENDPOINT` | ❌ | `https://api.deepseek.com/chat/completions/` | عنوان نقطة نهاية API |
| `LLM_API_MODEL` | ❌ | `deepseek-v4-flash` | اسم النموذج المستخدم |

### قالب التعليمات المخصص

لتعديل تنسيق الخروج، قم بتحرير ملف `.github/workflows/scripts/template.txt`:

```txt
أنت مهندس توثيق تطوير البرمجيات. يرجى إنشاء سجل تغييرات (Changelog) منظم، مقروء ومتстандарت بناءً على سجلات Git التالية:
المتطلبات:
1. الخروج بتنسيق Markdown، مخصص لشكل توثيق مشروع App
2. التصنيف: ميزات جديدة، تحسينات الأداء، إصلاحات أخطاء، إعادة هيكلة الكود، تحديثات التبعيات
3. لغة موجزة رسمية، استبعاد وصفات مراجع merge وغير صالحة وwip
4. رأس עם رقم الإصدار الرئيسي، رقم الإصدار الكامل، العلامة الحالية، وتاريخ التحديث
5. فقط خروج نص Markdown الأساسي، بدون تفسيرات إضافية، بدون مقدمة
...
```

### مسار الملف الناتج

يمتلك مسار ملف سجل التغييرات المولود التنسيق التالي:
```
doc/Changelogs/{main_version}/{sub_version}/App.md
```

على سبيل المثال، عندما يكون `main_version=1`، `sub_version=1.2.3`، يكون مسار الملف:
```
doc/Changelogs/1/1.2.3/App.md
```

## 📁 بنية المشروع

```
.github/
├── workflows/
│   ├── generate-changelog.yml    # تعريف سير عمل GitHub Actions
│   └── scripts/
│       ├── gen_changelog.py      # سكربت التوليد الرئيسي
│       └── template.txt          # قالب تعليمات LLM
README.md                         # وثائق المشروع
```

### وصف الملفات الرئيسية

- **generate-changelog.yml**: تعريف سير عمل GitHub Actions مع العملية الكاملة للتوليد التلقائي
- **gen_changelog.py**: سكربت Python الذي يقرأ المراجع، يستدعي API LLM، ويحفظ النتائج
- **template.txt**: قالب التعليمات الذي يتحكم في تنسيق ومحتوى خروج LLM

1. **معلمات الإدخال**:

## ⚠️ ملاحظات

1. **تكاليف استدعاء API**: قد يتسبب استخدام API LLM في تكاليف. تأكد من فهم طريقة الفوترة للخدمة التي تستخدمها.
2. **استقرار الشبكة**: تأكد من أن GitHub Actions يمكنها الوصول إلى نقطة نهاية API LLM المحددة.
3. **جودة المراجع**: تتمد جودة سجل التغييرات المولود على وضوح وشاملية رسائل المراجع.
4. **إتقان تسمية العلامات**: يُنصح باستخدام تسميات الإصدارات семантиكية، مثل `v1.0.0`، `v2.1.3`، إلخ.
5. **متطلبات الصلاحيات**: يحتاج سير العمل إلى أذونات الكتابة في المستودع. تأكد من أن GitHub Actions لديها أذونات كافية.

## ❓ أسئلة مكررة

### س1: ماذا يحدث إذا لم تكن هناك علامة للإصدار السابق؟
ج: يحتوي سير العمل على آلية إعطاء ترحيب ذكية. إذا لم يتم العثور على علامة صالحة سابقة، فإنه يستخدم تلقائيًا آخر 20 سجلًا من المراجع كأساس للتوليد، مما يضمن أنه يمكن دائمًا توليد سجل تغييرات.

### س2: هل يمكنني استخدام خدمات LLM أخرى؟
ج: نعم. هذا المشروع متوافق مع أي خدمة LLM تقدم API بتنسيق OpenAI. ما عليك سوى تكوين `LLM_API_ENDPOINT` و `LLM_API_MODEL` المقابلة في Secrets.

### س3: إلى أي فرع سيتم إضافة ملف سجل التغييرات المولود؟
ج: يتم إضافته بشكل افتراضي إلى الفرع من которого تم تشغيل سير العمل (عادةً فرع `main`). تحدد تكوين سير العمل `ref: main` لضمان إجراء العملية في الفرع الرئيسي.

### س4: كيف يمكنني تعديل طريقة تصنيف سجل التغييرات؟
ج: قم بتحرير قالب التعليمات في ملف `.github/workflows/scripts/template.txt` وقم بضبط متطلبات التصنيف. على سبيل المثال، يمكنك إضافة فئات مثل "تحديثات أمان" أو "تحسينات التوثيق".

### س5: ماذا افعل إذا فشل استدعاء API؟
ج: سيرعرض GitHub Actions سجلات الخطأ تلقائيًا. الأسباب الشائعة تشمل: مفتاح API غير صالح، عدم الوصول الشبكي إلى نقطة نهاية API، تنسيق استجابة API غير متطابق، إلخ. تحقق من تكوين Secrets والاتصال بالشبكة.

### س6: هل يمكنني توليد سجلات تغييرات للعديد من الإصدارات في آن واحد؟
ج: نعم. أدخل معلمات رقم إصدار مختلفة في كل تشغيل يدوي لسير العمل لتوليد ملفات سجل التغييرات المستقلة لعديد من الإصدارات.

### س7: لماذا نحتاج إلى تاريخ Git الكامل؟
ج: تاريخ Git الكامل (`fetch-depth: 0`) ضروري لحساب اختلافات المراجع بين العلامات بدقة. هذا هو الأساس لإنشاء سجلات تحديثات الإصدارات الدقيقة.

## 🔄 التمديدات المخصصة

### دعم خدمات LLM الأخرى

لتغيير إلى خدمة LLM أخرى (مثل OpenAI، Claude، إلخ)، ما عليك سوى تعديل التكوينات التالية:

1. قم بتحديث `LLM_API_ENDPOINT` إلى عنوان API للخدمة المقابلة
2. قم بتحديث `LLM_API_MODEL` إلى اسم النموذج المقابل
3. تأكد من أن تنسيق استجابة API متطابق مع DeepSeek (يعيد `choices[0].message.content`)

### تعديل تنسيق الخروج

عن طريق تحرير ملف `template.txt`، يمكنك تخصيص تنسيق الخروج بالكامل، على سبيل المثال:
- ضبط التصنيف
- تعديل الرموز التعبيرية
- إضافة أقسام مخصصة
- تغيير نمط المستند
