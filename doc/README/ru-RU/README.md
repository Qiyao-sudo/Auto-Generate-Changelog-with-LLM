# 🚀 Автоматическая генерация Changelog с использованием LLM

🌐 **Языки**: [English](doc/README/en-US/README.md) | [中文](doc/README/zh-CN/README.md) | [日本語](doc/README/ja-JP/README.md) | [Deutsch](doc/README/de-DE/README.md) | [Español](doc/README/es-ES/README.md) | [Русский](doc/README/ru-RU/README.md) | [العربية](doc/README/ar-SA/README.md) | [繁體中文](doc/README/zh-TW/README.md)

Автоматический инструмент на основе GitHub Actions, который использует большие языковые модели (LLM), такие как DeepSeek, для автоматической генерации стандартизированных, структурированных журналов версионных обновлений (Changelog). Нет необходимости вручную писать - просто запустите рабочий процесс и получите профессиональную документацию обновлений.

## ✨ Функции

- 🤖 **Интеллектуальный анализ**: На основе LLM для интеллектуального анализа записей Git, автоматической категоризации на новые функции, оптимизации производительности, исправления ошибок и т.д.
- 🏷️ **Автоматическое управление тегами**: Поддерживает автоматическое создание тегов Git и интеллектуальный расчет различий между версиями.
- 📁 **Структурированное хранение**: Хранит сгенерированные документы Changelog иерархически по основной версии и подверсии.
- 🎨 **Профессиональные шаблоны**: Предоставляет стандартизированные Markdown-шаблоны с единым и привлекательным форматом вывода.
- 🔧 **Высококонфигурируемый**: Поддерживает пользовательские API LLM, модели, шаблоны запросов и другие параметры.
- ⚡ **Одно-click запуск**: Ручной запуск через GitHub Actions, просто введите номер версии для автоматической генерации.

## 🚀 Быстрый старт

### Предварительные требования

1. **Репозиторий GitHub**: GitHub Actions включен
2. **Ключ API LLM**: Ключ API для DeepSeek или других сервисов LLM, совместимых с API OpenAI
3. **Среда Python**: Ubuntu-окружение в GitHub Actions (автоматически настроено)

### Шаги установки

1. **Скопируйте файл рабочего процесса**: Скопируйте `.github/workflows/generate-changelog.yml` в тот же путь вашего репозитория
2. **Скопируйте файлы скриптов**: Скопируйте директорию `.github/workflows/scripts/` в ваш репозиторий
3. **Настройте Secrets**: Добавьте следующие Secrets в Настройки репозитория → Secrets and variables → Actions:
   - `LLM_API_KEY`: Ваш ключ API LLM
   - (Необязательно) `LLM_API_ENDPOINT`: Конечная точка API LLM, по умолчанию DeepSeek
   - (Необязательно) `LLM_API_MODEL`: Название используемой модели, по умолчанию `deepseek-chat`

## 📖 Использование

### Ручной запуск рабочего процесса

1. Перейдите на страницу **Actions** вашего репозитория GitHub
2. Выберите рабочий процесс **Auto Generate Changelog with DeepSeek**
3. Нажмите кнопку **Run workflow**
4. Введите следующие параметры:
   - **main_version**: Номер основной версии (например, `1.X`)
   - **sub_version**: Полный номер версии (например, `1.X.X`)
   - **current_tag**: Название текущего тега Git (например, `v1.X.X`, будет автоматически создан, если не существует)

### Процесс выполнения рабочего процесса

1. **Выборка кода**: Выборка полной истории Git и всех тегов
2. **Обработка тегов**: Проверка наличия указанного тега, создание, если не существует
3. **Анализ различий коммитов**: Интеллектуальный расчет различий коммитов с предыдущей версией
4. **Генерация LLM**: Вызов API DeepSeek для генерации структурированного Changelog
5. **Сохранение файла**: Сохранение сгенерированного документа в `doc/Changelogs/{основная версия}/{подверсия}/App.md`
6. **Автоматический коммит**: Коммит сгенерированного файла Changelog в репозиторий
7. **Push тега**: Если это новый тег, автоматический push в удаленный репозиторий

## ⚙️ Инструкции по настройке

### Настройка переменных окружения

Настройте следующие переменные в GitHub Secrets:

| Название переменной | Обязательно | Значение по умолчанию | Описание |
|--------------------|------------|------------------------|----------|
| `LLM_API_KEY` | ✅ | Нет | Ключ API LLM |
| `LLM_API_ENDPOINT` | ❌ | `https://api.deepseek.com/chat/completions/` | Адрес конечной точки API |
| `LLM_API_MODEL` | ❌ | `deepseek-chat` | Название используемой модели |

### Пользовательский шаблон запроса

Чтобы изменить формат вывода, отредактируйте файл `.github/workflows/scripts/template.txt`:

```txt
Вы являетесь инженером по документации разработки программного обеспечения. Пожалуйста, сгенерируйте структурированный, читаемый и стандартизированный журнал версионных обновлений (Changelog) на основе следующих записей Git:
Требования:
1. Вывод в формате Markdown, адаптированный под стиль документации проекта App
2. Категоризация: Новые функции, Оптимизации производительности, Исправления ошибок, Рефакторинг кода, Обновления зависимостей
3. Лаконичный и официальный язык, исключая无效的 merge- и wip-описания коммитов
4. Заголовок с номером основной версии, полным номером версии, текущим тегом и датой обновления
5. Только вывод основного текста Markdown, без дополнительных объяснений, без вступления
...
```

### Путь к выходному файлу

Путь к сгенерированному файлу Changelog имеет следующий формат:
```
doc/Changelogs/{main_version}/{sub_version}/App.md
```

Например, при `main_version=1`, `sub_version=1.2.3` путь к файлу будет:
```
doc/Changelogs/1/1.2.3/App.md
```

## 📁 Структура проекта

```
.github/
├── workflows/
│   ├── generate-changelog.yml    # Определение рабочего процесса GitHub Actions
│   └── scripts/
│       ├── gen_changelog.py      # Основной скрипт генерации
│       └── template.txt          # Шаблон запроса LLM
README.md                         # Документация проекта
```

### Описание ключевых файлов

- **generate-changelog.yml**: Определение рабочего процесса GitHub Actions с полным процессом автоматической генерации
- **gen_changelog.py**: Python-скрипт, который читает коммиты, вызывает API LLM и сохраняет результаты
- **template.txt**: Шаблон запроса, который контролирует формат и содержимое вывода LLM

## ⚠️ Примечания

1. **Расходы на вызов API**: Использование API LLM может генерировать расходы. Убедитесь, что вы понимаете метод выставления счетов используемого сервиса.
2. **Стабильность сети**: Убедитесь, что GitHub Actions может получить доступ к настроенной конечной точке API LLM.
3. **Качество коммитов**: Качество сгенерированного Changelog зависит от ясности и полноты сообщений коммитов.
4. **Конвенция именования тегов**: Рекомендуется использовать семантическое версионирование, например `v1.0.0`, `v2.1.3` и т.д.
5. **Требования к правам**: Рабочий процесс нуждается в правах на запись в репозиторий. Убедитесь, что GitHub Actions имеет достаточные права.

## ❓ Часто задаваемые вопросы

### Q1: Что произойдет, если нет тега предыдущей версии?
A: Рабочий процесс имеет интеллектуальный механизм обратного отката. Если не найден предыдущий действительный тег, автоматически использует последние 20 записей коммитов в качестве основы для генерации, обеспечивая, что Changelog всегда может быть сгенерирован.

### Q2: Можно ли использовать другие сервисы LLM?
A: Да. Этот проект совместим с любым сервисом LLM, который предоставляет API в формате OpenAI. Просто настройте соответствующие `LLM_API_ENDPOINT` и `LLM_API_MODEL` в Secrets.

### Q3: В какую ветку будет закоммичен сгенерированный файл Changelog?
A: По умолчанию закоммичен в ветку, из которой был запущен рабочий процесс (обычно ветка `main`). Конфигурация рабочего процесса указывает `ref: main` для обеспечения выполнения операции в главной ветке.

### Q4: Как изменить способ категоризации Changelog?
A: Отредактируйте шаблон запроса в файле `.github/workflows/scripts/template.txt` и скорректируйте требования к категоризации. Например, вы можете добавить категории, такие как "Безопасность обновления" или "Улучшения документации".

### Q5: Что делать, если вызов API неудачен?
A: GitHub Actions автоматически покажет логи ошибок. Частые причины включают: недействительный ключ API, недоступность сетевого доступа к конечной точке API, несовместимый формат ответа API и т.д. Проверьте конфигурацию Secrets и сетевое соединение.

### Q6: Можно ли генерировать Changelog для нескольких версий одновременно?
A: Да. Введите разные параметры номера версии при каждом ручном запуске рабочего процесса для генерации независимых файлов Changelog для разных версий.

### Q7: Почему нужна полная история Git?
A: Полная история Git (`fetch-depth: 0`) необходима для точного расчета различий коммитов между тегами. Это основа для создания точных журналов версионных обновлений.

## 🔄 Пользовательские расширения

### Поддержка других сервисов LLM

Чтобы переключиться на другой сервис LLM (например, OpenAI, Claude и т.д.), просто измените следующие конфигурации:

1. Обновите `LLM_API_ENDPOINT` до адреса API соответствующего сервиса
2. Обновите `LLM_API_MODEL` до названия соответствующей модели
3. Убедитесь, что формат ответа API совместим с DeepSeek (возвращает `choices[0].message.content`)

### Изменение формата вывода

Редактированием файла `template.txt` вы можете полностью настроить формат вывода, например:
- Настройка категоризации
- Изменение эмодзи
- Добавление пользовательских разделов
- Изменение стиля документа
