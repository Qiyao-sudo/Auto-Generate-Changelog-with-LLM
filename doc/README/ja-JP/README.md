# 🚀 LLMによる自動Changelog生成

🌐 **言語**: [English](doc/README/en-US/README.md) | [中文](doc/README/zh-CN/README.md) | [日本語](doc/README/ja-JP/README.md) | [Deutsch](doc/README/de-DE/README.md) | [Español](doc/README/es-ES/README.md) | [Русский](doc/README/ru-RU/README.md) | [العربية](doc/README/ar-SA/README.md) | [繁體中文](doc/README/zh-TW/README.md)

DeepSeekなどの大規模言語モデル（LLM）を活用して、GitHub Actions上で自動的に標準化された構造化バージョン変更ログ（Changelog）を生成する自動化ツールです。手動での記述は不要で、ワークフローをトリガーするだけでプロフェッショナルレベルの更新ドキュメントを取得できます。

## ✨ 機能特長

- 🤖 **インテリジェント分析**: LLMを使用してGitコミット記録をインテリジェントに分析し、新機能、パフォーマンス最適化、バグ修正などのカテゴリに自動的に分類します
- 🏷️ **自動タグ管理**: Gitタグの自動作成をサポートし、バージョン範囲の差分をインテリジェントに計算します
- 📁 **構造化ストレージ**: メジャーバージョンとマイナーバージョンごとに階層構造で生成されたChangelogドキュメントを保存します
- 🎨 **プロフェッショナルテンプレート**: 美的に統一された出力のための標準化されたMarkdownテンプレートを提供します
- 🔧 **高度な設定**: カスタムLLM API、モデル、プロンプトテンプレートなどのパラメータをサポートします
- ⚡ **ワンクリックトリガー**: GitHub Actionsを介した手動トリガーで、バージョン番号を入力するだけで自動生成します

## 🚀 クイックスタート

### 前提条件

1. **GitHubリポジトリ**: GitHub Actionsが有効になっていること
2. **LLM APIキー**: DeepSeekまたは他のOpenAI API互換のLLMサービスAPIキー
3. **Python環境**: GitHub Actions内のUbuntu環境（自動的に構成されます）

### インストール手順

1. **ワークフローファイルのコピー**: `.github/workflows/generate-changelog.yml` をあなたのリポジトリの同じパスにコピーします
2. **スクリプトファイルのコピー**: `.github/workflows/scripts/` ディレクトリをあなたのリポジトリにコピーします
3. **Secretsの設定**: リポジトリの Settings → Secrets and variables → Actions で以下のSecretsを追加します:
   - `LLM_API_KEY`: あなたのLLM APIキー
   - （オプション）`LLM_API_ENDPOINT`: LLM APIエンドポイント、デフォルトはDeepSeek
   - （オプション）`LLM_API_MODEL`: 使用するモデル名、デフォルトは `deepseek-v4-flash`

## 📖 使用方法

### 手動ワークフロートリガー

1. GitHubリポジトリの **Actions** ページに移動します
2. **Auto Generate Changelog with DeepSeek** ワークフローを選択します
3. **Run workflow** ボタンをクリックします
4. 以下のパラメータを入力します:
   - **main_version**: メジャーバージョン番号（例: `1.X`）
   - **sub_version**: 完全なバージョン番号（例: `1.X.X`）
   - **current_tag**: 現在のGitタグ名（例: `v1.X.X`、存在しない場合は自動的に作成されます）

### ワークフロー実行プロセス

1. **コードのチェックアウト**: 完全なGit履歴とすべてのタグを取得します
2. **タグ処理**: 指定されたタグが存在するか確認し、存在しない場合は自動的に作成します
3. **コミット差分分析**: 前のバージョンからのコミット差分をインテリジェントに計算します
4. **LLM生成**: DeepSeek APIを呼び出して構造化されたChangelogを生成します
5. **ファイル保存**: 生成されたドキュメントを `doc/Changelogs/{メジャーバージョン}/{サブバージョン}/App.md` に保存します
6. **自動コミット**: 生成されたChangelogファイルをリポジトリにコミットします
7. **タグプッシュ**: 新しいタグが作成された場合、自動的にリモートリポジトリにプッシュします

## ⚙️ 設定

### 環境変数の設定

GitHub Secretsで以下の変数を設定します:

| 変数名 | 必須 | デフォルト値 | 説明 |
|--------|------|--------------|------|
| `LLM_API_KEY` | ✅ | なし | LLM APIキー |
| `LLM_API_ENDPOINT` | ❌ | `https://api.deepseek.com/chat/completions/` | APIエンドポイントアドレス |
| `LLM_API_MODEL` | ❌ | `deepseek-v4-flash` | 使用するモデル名 |

### カスタムプロンプトテンプレート

出力形式を変更するには、`.github/workflows/scripts/template.txt` ファイルを編集します:

```txt
あなたはソフトウェア開発ドキュメントエンジニアです。以下のGitコミット記録に基づいて、標準化された、読みやすく、構造化されたバージョンチェンジログを生成してください：
要件：
1. Markdown形式で出力し、Appプロジェクトドキュメントスタイルに適応させる
2. カテゴリ分け：新機能、パフォーマンス最適化、バグ修正、コードリファクタリング、依存関係更新
3. 言語は簡潔でフォーマルに、無効なmerge/wipコミット説明を削除する
4. ヘッダーにメジャーバージョン、完全バージョン、現在のタグ、更新日付を含める
5. 純粋なMarkdown本文のみを出力し、追加の説明や冒頭の挨拶は含めない
...
```

### 出力ファイルパス

生成されたChangelogファイルのパス形式:
```
doc/Changelogs/{main_version}/{sub_version}/App.md
```

例えば、`main_version=1`, `sub_version=1.2.3` の場合、ファイルパスは:
```
doc/Changelogs/1/1.2.3/App.md
```

## 📁 プロジェクト構造

```
.github/
├── workflows/
│   ├── generate-changelog.yml    # GitHub Actionsワークフロー定義
│   └── scripts/
│       ├── gen_changelog.py      # メイン生成スクリプト
│       └── template.txt          # LLMプロンプトテンプレート
README.md                         # プロジェクトドキュメント
```

### コアファイルの説明

- **generate-changelog.yml**: GitHub Actionsワークフロー定義、完全な自動生成プロセスを含む
- **gen_changelog.py**: Pythonスクリプト、コミット記録の読み取り、LLM APIの呼び出し、生成結果の保存を担当
- **template.txt**: プロンプトテンプレート、LLM出力形式とコンテンツ構造を制御

## ⚠️ 重要な注意事項

1. **API呼び出しコスト**: LLM APIの使用にはコストがかかる場合があります。選択したサービスの課金方法を理解してください
2. **ネットワーク安定性**: GitHub Actionsが設定されたLLM APIエンドポイントにアクセスできることを確認してください
3. **コミット記録の品質**: 生成されるChangelogの品質は、コミットメッセージの明確さと完全性に依存します
4. **タグ命名規則**: セマンティックバージョニング命名の使用を推奨します（例: `v1.0.0`、`v2.1.3`）
5. **権限要件**: ワークフローにはリポジトリへの書き込み権限が必要です。GitHub Actionsに十分な権限があることを確認してください

## ❓ よくある質問

### Q1: 前のバージョンのタグがない場合、どうなりますか？
A: ワークフローにはインテリジェントなフォールバックメカニズムがあります。有効な前のタグが見つからない場合、最新の20件のコミット記録を生成の基準として自動的に使用し、常にChangelogを生成できるようにします。

### Q2: 他のLLMサービスを使用できますか？
A: はい。このプロジェクトは、OpenAI形式のAPIを提供する任意のLLMサービスと互換性があります。Secretsで対応する `LLM_API_ENDPOINT` と `LLM_API_MODEL` を設定するだけです。

### Q3: 生成されたChangelogファイルはどのブランチにコミットされますか？
A: デフォルトでは、ワークフローがトリガーされたブランチ（通常は `main` ブランチ）にコミットされます。ワークフロー設定では `ref: main` が指定されており、メインブランチでの操作を保証します。

### Q4: Changelogの分類方法を変更するにはどうすればよいですか？
A: `.github/workflows/scripts/template.txt` ファイル内のプロンプトを編集して、分類要件を調整します。例えば、「セキュリティ更新」や「ドキュメント改善」などのカテゴリを追加できます。

### Q5: API呼び出しが失敗した場合はどうなりますか？
A: GitHub Actionsは自動的にエラーログを表示します。一般的な原因は次のとおりです：無効なAPIキー、ネットワークがAPIエンドポイントにアクセスできない、API応答形式が互換性がないなど。Secrets設定とネットワーク接続性を確認してください。

### Q6: 複数のバージョンのChangelogを同時に生成できますか？
A: はい。異なるバージョンパラメータでワークフローを手動でトリガーするたびに、異なるバージョンに対して独立したChangelogファイルを生成できます。

### Q7: 完全なGit履歴が必要なのはなぜですか？
A: 完全なGit履歴（`fetch-depth: 0`）は、タグ間のコミット差分を正確に計算するために必要です。これは正確なバージョン変更ログを生成するための基本です。

## 🔄 カスタム拡張

### 他のLLMサービスのサポート

他のLLMサービス（例：OpenAI、Claudeなど）に切り替えるには、以下の設定を変更するだけです:

1. `LLM_API_ENDPOINT` を対応するサービスのAPIアドレスに更新します
2. `LLM_API_MODEL` を対応するモデル名に更新します
3. API応答形式がDeepSeekと互換性があることを確認します（`choices[0].message.content` を返す）

### 出力形式の変更

`template.txt` ファイルを編集することで、出力形式を完全にカスタマイズできます。例：
- 分類方法の調整
- 絵文字シンボルの変更
- カスタムセクションの追加
- ドキュメントスタイルの変更
